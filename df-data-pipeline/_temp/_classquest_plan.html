方案 A 与 5 人本任务页同一套骨架（左列表 520 / 右详情 392 的同款结构，这里按职业页 748 宽重算成 268 + 472）。 方案 B 把「总奖励」并进每一行右侧，点行在下方内联展开完整详情 —— 更省横向空间，但详情宽度只有约 700，长文本会变高。

落地要点（确认方案后再动手）

入口`TT.MODE_KEYS = { "rotation", "macro", "quest", "text" }`，`TT.MODE_TITLE.quest = L["职业任务"]`；渲染分发在 `TT.Render` 加 `elseif mode == "quest"`。按钮宽度是按个数自动算的，加第 4 个不用改坐标。
数据新建 Core/Data/Data_ClassQuests.lua：`ns.ClassQuests = { quests = { [id] = {nm,lv,req,f,races,s,e,items,spells} }, chains = { WARRIOR = {...} } }`，由 `_temp/gen_class_quests.py` 从 ClassQuestsForever 的 Data/*.lua 转换生成（禁手抄）。zhTW/enUS 目录各出一份。
任务名ClassQuestsForever 的数据是英文名，页面上一律先问客户端 `DG.QuestName(id)`（`GetTitleForQuestID` + `PrefetchQuestData` 预热），拿不到才回退表里的英文名。链条标题同理，取链内第一步的中文名。
状态复用 `DG.QuestDone / DG.QuestActive / DG.QuestState` 三态；链条进度 = 已完成步数 / 总步数；种族、阵营过滤按角色自身（换浏览种族做成列表头下拉）。
详情抽一份 `DG.QuestDetailPool`（现在池子建在 `U.dungeonQDetPool` 里，绑在副本详情的 child 上）→ 改成「可换父级」的建池函数，两处共用：标题 / 状态 / 可接等级 / 任务难度 / 起始·结束 + 地图按钮 / 阵营 / 职业 / 种族 / 前置 / 后续 / 任务需求 / 任务奖励 / 收获。
性能628 条任务全部走 `ns.PaintJob` 分帧；列表用固定行池 + 视口剔除（同 `CU.Cull`），链条折叠态只存内存（`ns.ClassQuestUI.open`），不进 `DB()`。
红线零注释、无 ID 溯源、界面署名只保留 wowhead 一条；物品 / 法术名一律运行时取客户端，不落库中文名。
