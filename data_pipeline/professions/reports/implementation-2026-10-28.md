# 专业学习资料流水线实施与验收记录

本次将独立采集、确定性生成、补充资料读取、严格缺失处理接入 dev。原始 129 个 Data 文件保留，数值冲突保留 dev，急救沿用原行为。只新增 `Core/Data/Data_ProfLearningSources.lua`，不扩充原生制作配方数组。

## 数据从哪里来

- 正式入口：`https://wago.tools/api/builds/wowf/latest`。本批采集开始、结束确认的版本为 **1.60.1.70658**，22 张 DB2 表均成功校验。
- 本次原始数据由新流水线在 Ubuntu 无图形环境实际下载；没有用本地客户端、旧 Lua、modularization、旧审计或历史生成物补缺。
- Wowhead 使用匿名兼容 HTTP 会话、无头 Chromium 校验与会话续用；默认并发 2、网页请求间隔 1 秒、最多 3 次尝试，连续校验失败会熔断并记录受阻。此机制不能保证源站放行。
- 最终响应清单共 4,880 条：175 条 verified（22 张 DB2、153 条网页）、4,683 条 sourceBlocked、19 条 parseError、3 条 sourceMissing。受阻包括主机熔断后未再请求的实体，不能把它们说成 4,683 次实际 HTTP 403。
- 当前发现清单与恢复前的历史候选数量不同；覆盖统计以保留的响应记录为分母，不能拿候选发现数量冒充成功率。

生成资料含 2,540 个参考技能、1,856 条确认学习路径；2,463 个技能仍有部分缺口。参考技能数量不等于新增原生配方数量。确认学习路径也不等于教材购买渠道已确认、价格已知或当前角色必然可学。

归档仅包含 manifest 及其引用的响应，逐文件记录 URL、版本、时间、SHA-256；排除恢复时产生但已不再引用的孤立文件。最终原始 ZIP 共 292 个成员，5,877,205 字节，SHA-256：

`729887211291de5ea2d30d4b83b84b6f860344dd06ec44a48d6fc69829b908c1`

完整逐技能缺口、路径、证据和来源状态在交付目录 `dist/prof-learning/1.60.1.70658/report.json`；`raw.zip` 为可携带原始包。游戏运行只加载约 148 KiB 的补充 Lua，不读取这些离线文件。

## 插件中的判断

- 按专业、技能索引惰性读取，只附加规范化配方视图；原生数组、语言加载条件、Data 顺序及 `DungeonsForeverDB` 入口保留。
- 仅 Forever 使用补充资料；不会因本地客户端版本不同而禁用整批资料。当前角色观察仍独立于静态来源。
- 同一路径内条件全部满足，多条路径任选一条。教材、训练师、任务分别判断；教材缺详情不会阻塞其他明确有效路径。
- 已学配方不再受历史学习限制阻塞，实际制作条件仍需检查。打开过训练师或没持有教材都不是不可学习的证明。
- 学习资格、教材采购和训练费使用同一选中路径。训练师路径不强制购买教材；共用教材只计一次；未知费用不会补成零；掉落和任务不视作保证可得的免费库存。
- 网页列出商人和报价不代表购买资格完整。必须有明确的获取条件或现有可信商人观察；不能把缺失的 conditionsKnown 当成 true。
- 数值按当前 dev 和明确角色观察优先；补充来源的不同门槛保留在诊断，不注入为另一条相反门槛。
- 数据缺口、条件不满足、角色信息未取得分别显示。缺口仅影响相应未学配方；保留已验证可达区间，不能到达目标时不显示完整费用或最优结论。
- 指纹变化会使候选失效，冻结计划保留步骤、收据和进度并提示重新计算；执行和学习步骤前再次校验。资料提供器意外缺失也不能绕过恢复检查。

具体例子：`5577 → 2671` 的教材关系已从本次 DB2 发现，但教材详情缺失，因此不能作为确认学习路径。技能 `23802` 的教材 `19447` 有已确认学习要求，获取资料仍不足；虚构拍卖报价不能使其可购买，实际持有教材时可以独立判断学习要求。`2329` 的明确训练师路径按已选路径计训练费，不强买图纸。

生成后的独立对比发现 34 条本专业学习技能门槛差异，全部保留 dev。例如 `2329` 来源为 15、dev 为 40；`2662` 来源为 15、dev 为 1；`2667` 来源为 80、dev 为 55。逐条结果在 [native-conflicts-2026-10-28.json](native-conflicts-2026-10-28.json)，该文件明确标记 `generationInput=false`，不能用作生成输入。

## 性能与 master 合并

补充资料按记录延迟展开，条件模板共享；冻结只复制实际涉及的资料。不会在游戏内联网、解析 JSON 或定时扫描全目录。后台求解每次回调只恢复一次协程，为发布和回收留出余量。

按 TOC 顺序加载全部 Data、三种语言及完整专业运行时，与实施前源码快照对比，离线 Lua 5.1 冷启动新增最大约 252.2 KiB，单专业强引用资料最大约 499.7 KiB，全部专业约 1,310 KiB，均低于计划内存预算。测量包含 Core/Hui/DungeonUI 及专业界面导出，但尚未分发初始化事件或创建真实客户端界面，打开专业后的真实角色缓存仍须游戏内验收。仅测补充提供器时的冷启动增量约 184 KiB，不能用它代表整套新增代码。

独占进程的 100 次交错采样中，炼金 Capture 的 p95 从 10.487 ms 到 10.128 ms（-3.42%）；这只覆盖指定操作和模拟角色场景，不能推广成所有界面操作都没有回退。

回调耗时采用独立脚本 `tests/benchmark_callbacks.py` 记录，默认测正常 Facade 调度，而不是只测兼容 runner。正常 `ProfRoutePlans` 和兼容 runner 的搜索切片均降至 0.5 ms，单次只恢复一个切片。正常调度的炼金已学、炼金未学、锻造已学三个场景，回调最大值分别为 1.236、1.379、1.738 ms，均低于 2 ms；包含原生结果发布、保存与执行刷新，未分发 UI 初始化和真实界面监听。

协作切片不是硬实时保证。此前兼容 runner 超过 2 ms 的原始样本仍保留在性能报告；真实客户端、可见 UI、长搜索及 GC 压力尚未验收，不能据本轮小场景样本宣称所有操作都达标。容器文件和摘要锁已提供，本机没有 Docker，未实际构建镜像；实际 Linux 验证来自无 GUI Ubuntu 虚拟环境。

以 master `698b48d7209000d3759a83ec0526c11aa328866f` 的归档建立隔离工作区，保留 master 原始 Data、版本及非专业模块，演练合入当前专业实现。三个重叠文件需要明确处理：`ProfRouteSolver.lua`、`ProfSolverRun.lua` 保留 dev 求解实现并兼容 master 协程调度；`ProfessionUI.lua` 使用完整 dev 专业界面，避免混合两套布局调用。其余作用域内文件通过三方合并检查。

隔离回归排除依赖退役私人来源快照的 13 个旧 CraftingA 证据测试，以及 2 个固定比较 dev Data 的旧测试；后两项由新交付检查直接对 master 原始 Data 和 TOC 验证替代。排除项逐个记录。此处是隔离快照演练，没有修改 master 分支，也不代表自动无冲突合并。
